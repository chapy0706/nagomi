# issue-04: 社員ホワイトリスト管理（employees テーブルとRLS）

## 概要・背景・目的

nagomi はサインアップを完全に閉じたホワイトリスト方式を採用する。
管理者が事前に登録した社員IDのみがログイン可能であり、その管理基盤を本 issue で構築する。

`auth.users`（Supabase Auth が管理する認証テーブル）とは別に `employees` テーブルを設けることで、退職時の無効化を「Authユーザー削除」ではなく「`is_active = false` のフラグ更新」で済ませる。これにより、過去ログとの整合性が崩れず、再雇用時の復活も容易になる。

## 受け入れ条件

- [ ] `employees` テーブルのマイグレーションが追加されている
- [ ] 9桁数値の社員IDに対する CHECK 制約が定義されている
- [ ] `is_active` フラグでの有効/無効管理が可能
- [ ] RLS が有効化され、以下のポリシーが設定されている
  - SELECT: ユーザーは自分自身のレコードのみ参照可能
  - INSERT/UPDATE/DELETE: service_role のみ可能
- [ ] 管理者用の Edge Function でホワイトリスト登録 API が実装されている（CLI/管理画面からの呼び出し前提）
- [ ] ローカル環境用のシードデータで複数の社員が登録できる
- [ ] RLS ポリシーの統合テストが Vitest で書かれている
- [ ] `make verify` がエラーを発生させない

## 技術的な検討事項

- `employees.auth_user_id` は最初NULLで作成し、初回ログイン時に紐付ける運用とする
- 社員IDの形式チェック（9桁）はDB（CHECK制約）とドメイン層（EmployeeId値オブジェクト）の二重で行う
- 退職処理は `is_active = false` の更新のみ。Authユーザーは削除しない
- 管理者APIは将来的に管理画面から呼び出すが、初期は CLI（Supabase CLI または curl）からの呼び出しで十分
- `display_name` の初期値は「User1」「User2」のような匿名形式とし、ユーザー自身が変更可能
