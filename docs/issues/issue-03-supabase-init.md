# issue-03: Supabase プロジェクト初期化とローカル開発環境構築

## 概要・背景・目的

nagomi の永続化層・認証・リアルタイム同期はすべて Supabase に委ねる方針である。
本 issue では Supabase プロジェクトの初期化と、開発者がローカルでフルスタックを起動できる環境を整える。

ローカル環境を最初に整える理由は、後続のすべての issue（特にRLS設計や認証フロー）で「実際にDBに繋いで動作確認できる」状態が前提になるため。クラウド共有のステージング環境に依存すると、複数人開発時の競合や無料枠消費の問題が出てくる。

## 受け入れ条件

- [ ] Supabase クラウドの本番プロジェクトとステージングプロジェクトが作成されている
- [ ] `supabase/config.toml` がリポジトリにコミットされている
- [ ] `supabase/migrations/` ディレクトリが存在し、空のマイグレーションが1本通っている
- [ ] `make db/up` でローカル Supabase にマイグレーションが適用できる
- [ ] `make db/reset` でローカルDBがクリーンに戻る
- [ ] `.env.example` に Supabase 関連の環境変数キーが記載されている
- [ ] README の「セットアップ」セクションに従って、第三者がローカル起動できる
- [ ] `make verify` がエラーを発生させない

## 技術的な検討事項

- ローカル Supabase は Docker ベースで起動する。Apple Silicon でも動作確認すること
- `SUPABASE_SERVICE_ROLE_KEY` はサーバ側コードのみで使用する。`.env.local` には記載するが `NEXT_PUBLIC_` プレフィックスは付けない
- 本番・ステージング・ローカルで Jitsi のドメインも切り替えられるよう環境変数化する
- マイグレーションファイルはタイムスタンプ付き命名規則を守る（`YYYYMMDDHHMMSS_description.sql`）
- 本番プロジェクトのバックアップ方針を確認しておく（無料枠の制約）
