# issue-08: フロア・部屋のドメインモデル実装

## 概要・背景・目的

nagomi のフロアと部屋の概念をドメイン層で表現する。
Floor（オープンフロア）、Lounge（雑談スペース）、MeetingRoom（会議室）の3種類があり、それぞれ異なる制約と振る舞いを持つ。

ドメインモデルを先に固めることで、後続のpresence同期・通話機能・UIが共通の語彙で実装できる。
ユビキタス言語をコードに落とし込むこの工程は、上流工程の説明力を養う上でも重要な経験になる。

## 受け入れ条件

- [ ] `Floor` エンティティが domain 層に実装されている
- [ ] `Lounge` エンティティが実装されている（定員2〜3人）
- [ ] `MeetingRoom` エンティティが実装されている（定員5人以上、複数室対応）
- [ ] `RoomCapacity` 値オブジェクトが実装され、定員ルールを内包する
- [ ] `Position` 値オブジェクトが実装され、座標範囲を検証する
- [ ] `Room` 共通インターフェース（または union type）で多態性が表現されている
- [ ] 部屋の物理レイアウト（座標範囲）は設定ファイルから読み込める構造
- [ ] ユニットテストで各エンティティと値オブジェクトがカバーされている
- [ ] `make verify` がエラーを発生させない

## 技術的な検討事項

- 部屋の物理レイアウト（座標、形状）は JSON または TypeScript の定数として外部化する
- 定員チェックロジックはドメインサービスとして分離するか、エンティティに持たせるかを検討
- 「フロアに入っている」「会議室に入っている」を排他状態として表現する（同時に複数の部屋には居ない）
- 将来的にフロアレイアウトを管理画面から編集する余地を残す（ハードコードしない）
- 30人規模の大規模交流会用フロアを別途定義するか、既存Floorのバリエーションとして扱うかを検討
