# issue-05: 9桁社員IDによる認証フロー実装（擬似メール方式）

## 概要・背景・目的

社員はメールアドレスを持たないが、Supabase Auth の仕組み（JWT、セッション管理、RLS連携）をそのまま活用したい。
そこで社員IDを擬似メール形式（`{employee_id}@employees.internal`）に変換して Supabase Auth に登録する方式を採用する。

ユーザーは画面上で社員IDのみを入力すれば良く、内部の擬似メール変換はドメイン層に閉じ込める。
この設計により、将来「実メールアドレスへの移行」「SSO導入」のような変更があっても、AuthGateway ポートの差し替えだけで対応できる。

## 受け入れ条件

- [ ] `EmployeeId` 値オブジェクトが domain 層に実装されている（9桁検証ロジック内包）
- [ ] `AuthGateway` ポートが domain 層に定義されている
- [ ] `SupabaseAuthGateway` が infrastructure 層に実装されている
- [ ] `AuthenticateEmployee` ユースケースが application 層に実装されている
- [ ] 擬似メール変換ロジックは AuthGateway 実装内に閉じ込められている（domain 層は擬似メールを知らない）
- [ ] ログイン画面のUIが Tailwind + shadcn で実装されている
- [ ] ログイン失敗時のメッセージが「社員IDまたはPINが正しくありません」（具体的な失敗理由を漏らさない）
- [ ] employees テーブルで is_active = false のユーザーはログインできない
- [ ] ユニットテストでドメイン層・ユースケース層がカバーされている
- [ ] `make verify` がエラーを発生させない

## 技術的な検討事項

- 擬似メールのドメイン部分 `@employees.internal` は予約済みTLDではないため、外部からのメール配信を絶対に行わない運用を徹底する
- パスワード（PIN）の最低要件はドメイン層で検証する（4桁数字、辞書攻撃対策で6桁推奨など要検討）
- ログイン試行回数制限は本 issue では実装しない（後続の運用基盤側で対応）
- セッション保持期間は Supabase Auth のデフォルトに従う（後で調整可能）
- 認証エラーはユーザーに優しい言葉で伝える（システムエラー文言を露出させない）
