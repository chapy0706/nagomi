# issue-16: 会議室入室とロビー画面

## 概要・背景・目的

会議室・大規模交流会フロアへの入室時、ユーザーは必ずロビー画面を1枚挟む。
マイク・カメラ設定の確認、利用同意の再確認、誰が参加中かの可視化を行ってから、本入室する。

ロビーを挟む理由は、突然の通話開始を防ぐためと、入室前に自分の状態を整えるため。
特に20代のユーザー層は「予期せぬ通話」に強いストレスを感じる傾向があるため、心の準備の時間を構造的に提供する。

## 受け入れ条件

- [ ] `EnterMeetingRoom` ユースケースが実装されている
- [ ] ロビー画面のUIが Tailwind + shadcn で実装されている
- [ ] ロビーには現在の参加者リスト（表示名・アバター）が表示される
- [ ] マイク・カメラのプレビューが表示される
- [ ] マイク・カメラのデバイス選択が可能
- [ ] 定員に達している場合は入室ボタンが無効化され、その旨が表示される
- [ ] 「参加することで利用ポリシーに同意したものとみなす」の文言が表示される
- [ ] 「参加する」ボタンを押すまで通話には接続されない
- [ ] 「キャンセル」で元の場所に戻る
- [ ] ロビー画面はモバイルでも快適に操作できる
- [ ] `make verify` がエラーを発生させない

## 技術的な検討事項

- マイク・カメラのプレビューは Jitsi の prejoin 機能ではなく、自前で getUserMedia を使う
- デバイス選択の値は localStorage に保存し、次回利用時にデフォルト適用する
- 参加者リストは presence データから取得する（Jitsi に入る前なので Jitsi 側からは取れない）
- ロビーで長居されるとリソース消費なので、5分でタイムアウトする仕組みも検討
- 利用ポリシー同意の再確認は、初回ログイン時の同意とは別の「通話時固有の同意」として扱う
