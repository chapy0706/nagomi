# issue-06: 初回ログイン時のPIN設定と利用同意フロー

## 概要・背景・目的

管理者はホワイトリスト登録時に初期PINを発行する。
初回ログイン時にユーザー自身が新しいPINを設定し、同時に利用同意（プライバシーポリシー・利用規約）を行うことで、本人性の担保と法的な同意取得を実現する。

利用同意を初回ログインに組み込む理由は、勤怠ログや通話ログを取得する以上、明示的な同意を本人から得ることが法的・倫理的に必須だから。同意フローを後回しにすると、ログを取り始めるタイミングが遅れて運用面で混乱する。

## 受け入れ条件

- [ ] 初回ログイン判定ロジックがユースケース層に実装されている（`consent_accepted_at` が NULL かで判定）
- [ ] PIN変更画面が実装されている（現PIN + 新PIN + 確認用入力）
- [ ] 新PINの強度ルールが domain 層で検証されている
- [ ] 利用同意画面が実装されている（プライバシーポリシー・利用規約の本文表示）
- [ ] 同意チェックボックスをONにしないと送信ボタンが有効化されない
- [ ] 同意完了時に `employees.consent_accepted_at` が更新される
- [ ] PIN変更・同意の両方を完了するまで他画面に遷移できない（ガード処理）
- [ ] プライバシーポリシー本文を docs/privacy-policy.md として管理している
- [ ] `make verify` がエラーを発生させない

## 技術的な検討事項

- プライバシーポリシーは Markdown で管理し、ビルド時にHTMLに変換して表示する
- 同意のバージョン管理を将来導入する余地を残す（カラムを `consent_version` も併設するか検討）
- PIN変更時は古いPINでの再認証を要求するが、初回は管理者発行PINが「古いPIN」となる
- 同意を撤回した場合の挙動は本 issue の範囲外とする（後続で検討）
- UIコピーは「ようこそ」「最初に簡単な設定をします」のような優しいトーンを心がける
