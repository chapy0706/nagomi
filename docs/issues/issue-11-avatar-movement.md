# issue-11: アバター移動とthrottle制御

## 概要・背景・目的

ユーザーがフロア上でアバターを動かせるようにする。
移動操作の即時性とリアルタイム通信のコスト（Realtime無料枠の消費）を両立させるため、クライアント側で throttle 制御を行う。

ナイーブに毎フレーム位置を送ると無料枠を即消費する。
「動いている間は200msに1回」「停止時は即時送信」のような戦略をクライアント側で実装することで、無料枠を月内に収める。

自分のアバターの操作中の位置は Zustand store のローカル状態として保持し、throttle を通して presence に送出する。store 上では「自分の位置」と「他者の位置」を分離し、自分の移動が他者アバターの再レンダリングを誘発しないようにする。

## 受け入れ条件

- [ ] `MoveAvatar` ユースケースが実装されている
- [ ] クリック移動またはドラッグ移動のUIが実装されている（実装方式は検討）
- [ ] 移動先座標の有効性が `Position` 値オブジェクトで検証される
- [ ] 部屋の境界・障害物との衝突判定が実装されている
- [ ] 自分の操作中の位置が Zustand store のローカル状態として管理されている
- [ ] 位置更新の送信頻度が 200ms に throttle されている
- [ ] 停止時には即時に最終位置が送信される
- [ ] 他ユーザーから見たアバター移動が滑らかに見える（補間アニメーション）
- [ ] モバイルでのタッチ操作にも対応している
- [ ] `make verify` がエラーを発生させない

## 技術的な検討事項

- throttle のロジックは presentation 層（useThrottledMove フック）に置く（ドメインの責務ではない）
- Zustand store 上で「自分の位置」と「他者の presence」をスライスとして分離する
- 補間は CSS transition または requestAnimationFrame で実装する
- 移動アニメーションの所要時間は 200ms 程度（throttle と揃える）
- 物理シミュレーション的な挙動（慣性、加速）は今回は実装しない（複雑化を避ける）
- モバイルでは画面サイズの問題でズーム機能が必要か検討
- 移動操作のキーボードショートカット（矢印キー）にも対応するか検討
