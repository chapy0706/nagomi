# issue-27: エラートラッキング導入

## 概要・背景・目的

本番環境で発生するエラーを検知・追跡するため、エラートラッキング基盤を導入する。
ユーザーが沈黙のうちに困っている状態（エラーで動かない、画面が真っ白）を早期発見することが目的。

無料枠で運用可能なサービスを選定する。
個人特定情報を送信しないよう、初期設定の段階でPII（個人識別情報）のスクラブ設定を徹底する。

## 受け入れ条件

- [ ] エラートラッキングサービスが選定され、プロジェクトが作成されている
- [ ] サーバ側・クライアント側の両方でエラー捕捉が設定されている
- [ ] PII（社員ID、表示名、IPアドレス等）が送信データから除外されている
- [ ] ソースマップがアップロードされ、本番エラーが読みやすい形で表示される
- [ ] エラー発生時の通知（Slack や メール）が設定されている
- [ ] ユーザー側にはエラー情報を露出させない（汎用的なエラー画面のみ）
- [ ] エラートラッキングを介した個人追跡が技術的にできないことが確認されている
- [ ] プライバシーポリシーにエラートラッキング利用が明記されている
- [ ] `make verify` がエラーを発生させない

## 技術的な検討事項

- 候補: Sentry（無料枠で月5,000イベント）、Better Stack、自前のログ集約など
- Sentry の場合、`beforeSend` フックで PII スクラブを徹底する
- セッションリプレイ機能は利用しない（プライバシー保護のため）
- 開発環境ではコンソール出力のみとし、本番環境のみ送信
- エラー通知の頻度制御（同じエラーが連続する場合のレート制限）
- 通報機能で発生する Edge Function のエラーも捕捉対象に含める
