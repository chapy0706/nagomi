# issue-14: 通話招待ドメインと招待フロー（IssueCallInvitation）

## 概要・背景・目的

nagomi の通話は「近づいたら自動接続」ではなく、必ず明示的な合意ステップを挟む。
本 issue では「招待を発行する」ユースケースと、招待状態を表現するドメインモデルを実装する。

合意ベースの設計は、就業後のゆるい交流空間としての心理的安全性を担保する核心。
「気軽に話しかけられる」と「いきなり話しかけられて困る」の境界を、UXで丁寧に区切る。

## 受け入れ条件

- [ ] `CallInvitation` エンティティが domain 層に実装されている
- [ ] 招待の状態（pending / accepted / declined / expired）が型で表現されている
- [ ] `IssueCallInvitation` ユースケースが実装されている
- [ ] 招待発行時にブロック関係がチェックされる
- [ ] 招待発行時に対象ユーザーのステータス（busy 等）がチェックされる
- [ ] 招待は Supabase Realtime Broadcast で対象クライアントに通知される
- [ ] 招待は call_invitations テーブルに記録される（追記のみ）
- [ ] 招待発行時のUI（モーダル）が実装されている
- [ ] ユニットテストでビジネスルールがカバーされている
- [ ] `make verify` がエラーを発生させない

## 技術的な検討事項

- 招待のチャネル名: `invitations:{employee_auth_id}` で個別購読
- 招待ペイロード: 招待ID、招待者表示名・アバター、トピック種別、有効期限
- 招待テーブルは追記のみ。状態遷移（accepted/declined/expired）は別途状態遷移ログとして追記するか、終了状態の確定のみ限定的に更新を許すかを検討（ログ追記の原則に従う）
- 同一相手への連続招待を防ぐクールダウン期間（例: 1分）を設けるか検討
- 招待履歴は通報対応の証跡にもなるため、最低30日は保持する
- 「招待された相手にだけ届く」設計を Realtime のチャネル分離で保証する
- 招待のドメインイベント発火を将来的に通知サービスに繋ぐ余地を残す
