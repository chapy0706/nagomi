# issue-18: ブロック機能（BlockRelation）

## 概要・背景・目的

ユーザー単位でブロック関係を持てるようにする。
ブロックされた相手からの招待は届かず、ブロック側からも相手のフロア上の存在を抑制的に扱う。

心理的安全性を機能で担保する重要な仕組み。
通報よりも軽い、自衛のための日常的なツールとして位置づける。

## 受け入れ条件

- [ ] `BlockRelation` エンティティが domain 層に実装されている
- [ ] `block_relations` テーブルのマイグレーションが追加されている
- [ ] RLS により、自分が関わる行のみ参照・操作可能
- [ ] `BlockEmployee` ユースケースが実装されている
- [ ] `UnblockEmployee` ユースケースが実装されている
- [ ] ブロック中のユーザーからの招待は届かない（IssueCallInvitation がブロックチェック）
- [ ] ブロック中のユーザーを自分のフロアから半透明・別レイヤーで表示する（完全に消すと不審）
- [ ] ブロックリスト管理画面が実装されている
- [ ] 招待モーダルから直接ブロックできる導線がある
- [ ] ブロックされた側は、ブロックされた事実を知らされない
- [ ] `make verify` がエラーを発生させない

## 技術的な検討事項

- ブロック関係は一方向（A→B のブロックがあっても B→A は別）
- block_relations はログ系ではなく状態を表すテーブルのため、ブロック解除に伴う DELETE を許容する（追記のみ制約の対象外）
- 完全に「相手を消す」と「相手も自分が消えたことに気づく」可能性があるため、自分側だけ抑制的にする
- 相互ブロックの場合は両方向で抑制が効く
- ブロック解除を躊躇なく行えるよう、UIは「軽く扱える」トーンにする
- 管理者は通報対応のためブロック関係を集計可能だが、個別の対人関係は閲覧しない設計とする
