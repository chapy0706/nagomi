  # Claude Code への指示書: nagomi-ws（Gleam/OTP WebSocket サーバー）

この指示書は issue-30 を Claude Code と並走して進めるためのもの。Gleam は初めてなので、各段階で「何をしているか」「なぜそうするか」を理解しながら進める。一気に全部を投げず、段階ごとに区切って指示する。

---

## 前提の共有（最初に Claude Code に伝える文脈）

```
私は Gleam/OTP が初めてです。各ステップで以下を守ってください。

1. コードを書く前に「これから何を作るか・なぜそうするか」を3-4行で説明する
2. Gleam 特有の概念（アクター、OTP、パターンマッチ等）が出たら、その都度簡潔に補足する
3. 一度に大量のコードを出さず、一つの責務ごとに区切る
4. 各ステップの最後に「動作確認の方法」を必ず示す
5. エラーが出たら、原因の切り分け方から一緒に考える

設計上の制約:
- nagomi 本体（Next.js）の src/domain/ は絶対に変更しない
- サーバーは「接続維持」と「メッセージ配信」だけを担う薄い中継点にする
- ビジネスロジックはサーバーに持たせない
- クライアント・サーバー間のメッセージ契約を型で明示する
- UNIX 哲学に従い、一つのことをうまくやる単機能の集合にする
```

---

## ステップ1: Gleam 開発環境（A1 上の Docker）

最初の指示例:

```
A1（aarch64 / ARM64・Ubuntu）上に、Gleam の開発環境を Docker コンテナで作りたいです。
以下を満たす構成を提案してください。

- Gleam と Erlang/OTP が入った開発用コンテナ
- ソースコードはホスト側にマウントして編集できる
- コンテナ内で gleam run / gleam test が実行できる
- aarch64 ネイティブで動く（エミュレーションを使わない）
- 最終的に Coolify でデプロイするので、開発用と本番用の Dockerfile を分けて考える

まず開発用コンテナの Dockerfile と docker-compose を作り、
「なぜこの構成か」を説明してから、起動確認の手順を示してください。
```

確認ポイント: `gleam --version` がコンテナ内で通ること。

---

## ステップ2: プロジェクト雛形と echo サーバー

```
nagomi-ws という Gleam プロジェクトを新規作成して、
まず最小の WebSocket echo サーバーを作りたいです。

- gleam new でプロジェクトを作る
- WebSocket ライブラリ（mist 等）を導入する
- クライアントから送られたメッセージをそのまま返す echo を実装する

Gleam の WebSocket ライブラリの選択肢と、なぜそれを選ぶかを説明してから、
最小実装を示してください。動作確認は wscat 等での接続方法も含めてください。
```

確認ポイント: ブラウザか wscat から接続して、送ったメッセージが返ること。

## ステップ3: OTP 接続管理アクター

```
次に、複数のクライアント接続を管理する仕組みを作りたいです。
Gleam/OTP のアクターモデルを使います。

私は OTP もアクターモデルも初めてなので、まず概念を説明してください。
- アクターとは何か
- なぜ「状態を持つプロセス」が接続管理に向いているか
- スーパーバイザーの役割

その上で、接続中のクライアント一覧を保持するアクターを実装してください。
接続・切断でリストが増減することを確認できる形にしてください。
```

確認ポイント: 2つ接続して1つ切断したとき、接続数が正しく増減すること。

## ステップ4: Presence チャンネル

```
接続管理アクターの上に Presence チャンネルを実装したいです。

責務:
- クライアントが自分の位置（x, y）と状態を送る
- サーバーは受け取った位置を、同じフロアの全接続にブロードキャストする
- サーバーはビジネス判断をしない（誰に送るか等の制御は後でクライアント側で行う）

メッセージ契約を最初に型として定義してください。
TypeScript 側と共有できるよう、契約の構造を明示してください。
2つのブラウザタブで位置が同期することを確認できる形にしてください。
```

確認ポイント: 2タブで一方の移動が他方に反映されること。

---

## ステップ5・6: Invitation / RoomActivity チャンネル

Presence が動いたら、同じパターンで Invitation と RoomActivity を追加する。

```
Presence チャンネルと同じ構造で、Invitation チャンネルを追加してください。
通話招待を特定のユーザーに配信する責務です。
Presence で確立したパターンを踏襲し、差分だけ説明してください。
```

確認ポイント: 招待が対象ユーザーにだけ届くこと。

---

## ステップ7: Next.js 側クライアント実装

```
nagomi 本体（Next.js）側に、WebSocket クライアント実装を追加したいです。

制約:
- src/domain/ports/ の PresenceGateway 等のインターフェースは変更しない
- src/infrastructure/websocket/ に新しい実装を置く
- 既存の src/infrastructure/supabase/ は削除しない
- ステップ4で定義したメッセージ契約に従う

PresenceGateway インターフェースを見せるので、それを満たす
WebSocketPresenceGateway を実装してください。
```

確認ポイント: 既存の Supabase 実装と同じインターフェースを満たすこと。

---

## ステップ8: 切り替え機構

```
Supabase 実装と WebSocket 実装を環境変数で切り替えられるようにしたいです。

- REALTIME_PROVIDER=supabase または websocket で切り替える
- DI（依存性注入）の組み立て部分だけで切り替わるようにする
- ドメイン層・アプリケーション層は変更しない

切り替えを担う factory または composition root を実装してください。
```

確認ポイント: 環境変数を変えるだけで両方式が動くこと。

## 進め方の原則

- 1ステップずつ進め、動作確認できてから次へ進む
- 詰まったら「区間で切り分ける」（接続できるか → メッセージが届くか → 配信されるか）
- 各ステップ完了時に、その時点の構成を nagomi リポジトリに commit する
- Gleam の新概念が出たら、立ち止まって意味記憶として理解してから進む
