# ADR-005: 通報者IDをスキーマに持たず、匿名性を構造的に保証する

## Context

nagomi は正社員派遣同士が交流する場であり、ハラスメントや不適切な利用への対抗手段として
通報機能を持つ。

通報機能を設計するにあたって、「通報者の匿名性をどう担保するか」が論点になった。
選択肢として「通報者IDを記録した上で、管理者のみが閲覧できるアクセス制御で守る」案と
「通報者IDをそもそも記録しない」案の2つを検討した。

この判断はプライバシー保護の強度と、nagomi のプロダクトとしての倫理的立場に直結する。

## Decision

`reports` テーブルに通報者を特定できるカラムを設けない。
Edge Function 経由で通報を受け付け、認証情報をDB書き込み前に剥がす。
通報者の身元はデータベースの構造として保存されない。

## Rationale

### スキーマで匿名性を担保する理由

**「アクセス制御で守る」は運用ルールへの依存になる。**
通報者IDを記録して管理者のみ閲覧可能にする設計は、
「その権限を誰が持つか」「権限が正しく設定されているか」という
運用・設定の正確さに匿名性の保証を依存させる。
設定ミス・権限の付与ミス・内部不正があれば通報者が特定されうる。

**スキーマで持たなければ、SQL で特定する手段が存在しない。**
カラム自体がなければ、どれだけ強い権限を持つユーザーでも
通報者をデータから特定できない。「運用で守る」ではなく
「構造として守る」ことで、保護の強度が設定に依存しなくなる。

**通報のしやすさがサービスの安全性を決める。**
nagomi は20代の新人が就業後にふらっと立ち寄る場所を志向している。
「通報したら自分が特定されるかもしれない」という不安があると、
悪意ある行動に対して沈黙するしかなくなる。
通報者が特定されないことを構造として保証することで、
利用者が安心して自衛手段を使える環境を作る。

**「プライバシーを機能で担保する」というnagomiの設計原則と一致する。**
`satisfaction_responses` も同様に employee_id を持たない。
nagomi は「個人を特定しない」という倫理的判断を、
運用ルールではなくデータモデルで表現するという方針を一貫させる。

## Consequences

### 良い結果

- 通報者の身元がデータ構造として存在しないため、内部関係者でも特定できない
- 利用者が「通報したら特定される」という不安を持たずに通報機能を使える
- プライバシー保護の説明責任を、設定ではなく構造で果たせる

### 引き受けるトレードオフ

- 同一人物による反復通報（嫌がらせ目的の乱用）を通報者単位で検知できない。
  対策として、通報内容のカテゴリ・対象・文面パターンによる集計的な検知を行う
- 通報の信憑性確認が難しくなる。管理者は通報内容の客観的な判断に頼る必要がある
- 通報を取り消す仕組みが作れない（誰が送ったか分からないため）。
  これは許容する（送信前の確認ステップで代替する）

### 今後の見直し条件

以下のいずれかが発生した場合、本 ADR を見直す。

- 反復通報による乱用が実際の運用問題になり、通報者の追跡が必要と判断された
- 法的な要件（例：特定の通報には発信者情報の保全が必要）が発生した
