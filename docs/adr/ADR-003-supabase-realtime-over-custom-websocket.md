# ADR-003: リアルタイム同期に Supabase Realtime を選択し、自前 WebSocket サーバー（Render）を不採用とした

## Context

nagomi はフロア上のアバター位置・在席ステータス・招待通知をリアルタイムで同期する必要がある。
同時接続50人規模で、アバターが動くたびに位置を他の全員に伝える、という通信が常時発生する。

選択肢として「Supabase Realtime の Presence + Broadcast を使う」案と
「Render 上に自前 WebSocket サーバーを立てる」案を検討した。
無料運用・サーバー管理コスト・nagomi のアーキテクチャ方針の3軸で判断する。

## Decision

リアルタイム同期基盤として **Supabase Realtime（Presence + Broadcast）** を採用する。
Render 上への自前 WebSocket サーバーの構築は不採用とする。

## Rationale

### Supabase Realtime を選んだ理由

**サーバーを持たなくていい。**
nagomi はすでに認証・DB・ストレージを Supabase に委ねている。
Realtime もそこに乗せることで、運用・監視・障害対応の対象がひとつのプラットフォームに集約できる。
自前 WebSocket サーバーを持つと、接続の復旧・スケール・モニタリングが別の運用負荷になる。

**Presence が「誰が今いるか」を最初から解いている。**
Supabase Realtime の Presence は、チャネルへの参加・離脱をサーバー側で追跡し、
接続が切れたユーザーを自動的に presence から除外する仕組みを持つ。
「ユーザーがブラウザを閉じた」「ネットワークが切れた」といったケースで
ゴースト（実態がないのに在席に見える）が残らない。
これを自前実装で再現するとハートビート管理・タイムアウト検知・再接続処理が必要になる。

**Broadcast で招待通知のチャネルも統一できる。**
アバター位置の同期（Presence）だけでなく、通話招待の通知（Broadcast）も
同じ Realtime の仕組みの上に乗せられる。通信路を一本化できる。

**Supabase の認証（JWT）と統合されている。**
Realtime への接続は Supabase Auth の JWT で認証される。
「ログインしていないユーザーが presence に接続できない」という制御が、
追加実装なしで成立する。

### Render での自前 WebSocket を不採用とした理由

**コールドスタートが体験を壊す。**
ADR-001 で Render を不採用とした理由と重なる。
Render の無料プランはスリープが発生し、コールドスタートに数十秒かかる。
「ふらっと立ち寄る」ユーザーが presence に接続しようとして数十秒待つ、
という体験は nagomi の存在意義を直接損なう。

**運用コストが増える。**
WebSocket サーバーの自前運用は、接続数の管理・再接続戦略・
負荷分散・障害検知といった関心を nagomi のチームが引き受けることを意味する。
プロダクトの価値（派遣社員の交流・短期離職低減）に直結しない運用負荷は
できる限り外部委託したい、という方針とぶつかる。

## Consequences

### 良い結果

- サーバーレスで presence 同期が成立する。運用対象が増えない
- Presence の退出追跡・Broadcast の配信が標準機能として利用できる
- Supabase の JWT 認証と Realtime が統合されており、認可ロジックが一箇所にまとまる
- アバター位置・ステータス・招待通知を同一の接続で扱える

### 引き受けるトレードオフ

- Supabase Realtime の無料枠は同時接続200・月200万メッセージ。
  50人 × 秒5回更新 × 日8時間 × 月20日 = 約2,880万メッセージとなりナイーブな実装では超過する。
  このため、位置更新を200msに throttle する・停止時のみ送信する、といった
  設計上の制約を最初から組み込む必要がある（issue-11 参照）
- Supabase Realtime の SLA はプランに依存する。無料枠では保証なし
- 複雑なルーティング（特定ユーザーにだけ送る、グループに送るなど）は
  チャネル設計で工夫が必要

### 今後の見直し条件

以下のいずれかが発生した場合、本 ADR を見直す。

- 同時接続・メッセージ数が無料枠を安定的に超えるようになった
- Supabase Realtime の可用性が業務要件に対して不十分と判断された
- より細かいルーティング制御が必要な機能要件が発生した
