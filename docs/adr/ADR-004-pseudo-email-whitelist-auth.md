# ADR-004: 認証に擬似メール方式のホワイトリストを採用し、カスタム認証・Magic Link を不採用とした

> **このADRは ADR-010 によって supersede された（2026-06-20）。**
> 認証基盤を Supabase Auth（擬似メール + PIN）から Keycloak（OIDC）へ移行する。
> 技術選定の根拠は ADR-009、ホワイトリストを業務属性として残す判断は ADR-010 を参照。
> 本ADRは経緯保存のため削除せず残す。

## Context

nagomi の認証には2つの固有の制約がある。

ひとつは「ユーザーはメールアドレスを持たない」。
利用者は派遣社員であり、共通のメールアドレスを持つ仕組みがない。
識別子として使えるのは9桁の社員ID のみ。

もうひとつは「完全なホワイトリスト方式にしたい」。
管理者が事前に登録した社員IDのみがログインできる構成が必要であり、
誰でもサインアップできる状態を一切許容しない。

一方で、Supabase Auth の仕組み（JWT・セッション管理・RLSとの統合）はそのまま活用したい。
Supabase Auth を活用しながら、メールアドレスなし・ホワイトリスト方式を両立させる設計が必要だった。

## Decision

認証方式として **擬似メール方式** を採用する。
社員ID（9桁）を `{employee_id}@employees.internal` 形式に変換して Supabase Auth に登録し、
`signInWithPassword` で認証する。

ホワイトリスト管理は `employees` テーブルで行い、`is_active` フラグによる有効/無効を管理する。
`auth.users` への登録は管理者の service_role 経由のみで行い、サインアップ経路を完全に閉じる。

カスタム認証基盤の構築・Magic Link・SMS OTP は不採用とする。

## Rationale

### 擬似メール方式を選んだ理由

**Supabase Auth の仕組みをそのまま使える。**
Supabase Auth は `email + password` 形式を前提とする。
社員IDを `@employees.internal` ドメインの擬似メールに変換することで、
JWT 発行・セッション管理・Cookie・RLS との統合（`auth.uid()` によるユーザー識別）が
追加実装なしでそのまま機能する。

**メール配信が絶対に発生しない。**
`@employees.internal` は実在しないドメインであり、外部へのメール送信が物理的に起きない。
「ユーザーにメールアドレスがない」という前提を壊さずに Supabase Auth に乗れる。

**擬似メール変換はインフラ層に閉じ込められる。**
`SupabaseAuthGateway` の実装の中だけに変換ロジックを閉じ込め、
ドメイン層は擬似メールの存在を知らない。
将来「実メールアドレスへの移行」「SSO 導入」のような変更があっても、
AuthGateway の差し替えだけで対応できる。

**`employees` テーブルと `auth.users` を分離することでホワイトリストが完全に閉じる。**
`employees` テーブルを「認証を許可する社員の台帳」として管理し、
`auth.users` への登録は service_role 経由のみにすることで、
一般ユーザーがサインアップする経路を構造的に存在させない。
退職処理も `is_active = false` のフラグ更新だけで済み、
`auth.users` の削除は不要。過去ログとの整合性が保てる。

### カスタム認証基盤を不採用とした理由

JWTの発行・セッション管理・Cookie のセキュリティ・トークンのリフレッシュを
自前で実装すると、セキュリティリスクと運用負荷が大幅に上がる。
Supabase Auth が解いている問題を再実装する理由がない。

### Magic Link を不採用とした理由

Magic Link は対象のメールアドレスにリンクを送る方式であり、
「メールアドレスを持たない」という今回の制約と根本的に相容れない。

### SMS OTP を不採用とした理由

社員の電話番号を収集・管理する仕組みが存在せず、
SMS 送信コストも発生する。管理コストに対してメリットが薄い。

## Consequences

### 良い結果

- Supabase Auth の標準機能（JWT・RLS統合・セッション管理）をそのまま使える
- ホワイトリスト管理と認証状態が分離されており、退職処理が `is_active` 更新だけで完結する
- 擬似メール変換がインフラ層に閉じているため、将来の認証方式変更の影響範囲が小さい
- サインアップ経路が構造的に存在しない（管理者 = service_role のみが登録可能）

### 引き受けるトレードオフ

- `@employees.internal` の擬似メールがコードに現れることがある。
  開発者が「なぜこのドメインか」を知らずにコードを読むと混乱する可能性がある。
  CLAUDE.md および本 ADR で理由を明示しておく
- Supabase Auth のパスワードポリシー・試行回数制限などに依存する部分がある

### 今後の見直し条件

以下のいずれかが発生した場合、本 ADR を見直す。

- 利用企業がメールアドレスを付与できるようになり、実メールへの移行要件が発生した
- SSO（SAML・OIDC）による認証が要件として浮上した
- Supabase Auth 以外の認証基盤への移行が必要になった
